# jvm — optimize-build stack reference
Use when: detect-stack.sh reported `jvm` (any Gradle or Maven project) and a test step is a hotspot. Lanes: test. Build-tool knobs are in [gradle.md](gradle.md) and [maven.md](maven.md); worker counts, forks and JUnit parallel settings are in `test-parallelism.md` §8.

Checked 2026-11-18. Latest that day: JUnit **6.1.3**, Spring Framework **7.0.10**, Spring Boot **4.1.2**, Testcontainers for Java **2.0.5**, Surefire **3.6.1**, Gradle **9.9.1**. **(cited)** means linked vendor text read that day. **(heuristic)** means typical but unmeasured, so measure it on the repo. No JDK was available for local runs, so nothing here is marked local.

## Measure
- **Slowest classes:** rank `target/surefire-reports/TEST-*.xml` or `build/test-results/**/*.xml` with the JUnit script in `ci-github-timings.md` §6. A class whose first test is slow and the rest fast is paying a startup cost (context, container, JVM), not a test cost.
- **Spring context starts:** set the log category `org.springframework.test.context.cache` to `DEBUG` to print cache statistics ([context caching](https://docs.spring.io/spring-framework/reference/testing/testcontext-framework/ctx-management/caching.html)). The miss count is the number of contexts built. A quicker proxy: count startup lines in the test log, `grep -cE 'Started \w+ in [0-9.]+ seconds' job.log`, and sum their seconds.
- **Container starts:** `grep -c 'Creating container for image' job.log` (Testcontainers), against the number of distinct images.
- **JVM forks:** read `forkCount`/`reuseForks` (Maven) or `maxParallelForks`/`forkEvery` (Gradle); grep commands are in the build-tool files.
- **What varies between test classes:**
  ```bash
  grep -rlE '@SpringBootTest|@WebMvcTest|@DataJpaTest' src/test | wc -l
  grep -rhoE '@(MockitoBean|MockitoSpyBean|MockBean|SpyBean|DirtiesContext|ActiveProfiles|TestPropertySource|DynamicPropertySource)' src/test | sort | uniq -c
  grep -rnE 'Thread\.sleep|@Container|withReuse|@Testcontainers' src/test | wc -l
  ```

## Checks
1. **Spring builds many application contexts.** **Facts** ([context caching](https://docs.spring.io/spring-framework/reference/testing/testcontext-framework/ctx-management/caching.html)): the cache key is made of the config locations and classes, initializers, context customizers (which include `@DynamicPropertySource` methods and bean overrides such as `@MockitoBean` and `@MockitoSpyBean`), the context loader, the parent, active profiles, test property sources and the resource base path. Any difference builds a new context. The cache holds 32 contexts by default (`spring.test.context.cache.maxSize`) and evicts least-recently-used ones. `@DirtiesContext` makes Spring "remove the context from the cache and rebuild the application context". **Check**: the number of context starts against the number of test classes; per-class sets of `@MockitoBean`; `@DirtiesContext`; per-class `properties = …`. **Fix**: one shared base class or meta-annotation carrying the full configuration and one shared set of mocks; reset state in place of `@DirtiesContext`; raise `maxSize` only when the suite has more than 32 distinct contexts for a reason. **Gain**: (contexts removed) × (startup seconds from the log) (arithmetic on measured numbers). **Risk**: shared mocks carry stubbing between classes, so reset them after each test.
2. **A new JVM per test class.** **Facts**: the context cache is static, so "all tests must run within the same process", and with per-test forking "the build process runs significantly more slowly as a result" (same page). Gradle: "Forking a JVM is an expensive operation" ([performance](https://docs.gradle.org/current/userguide/performance.html)). **Check**: Surefire `reuseForks=false`, or Gradle `forkEvery = 1`. **Fix**: `reuseForks=true`, `forkEvery = 0`, and repair the static-state leak that made the fresh JVM necessary. **Gain**: a JVM start, JIT warm-up and every cached context, per class (heuristic). **Risk**: tests that mutate static state or system properties start failing; isolate those in their own module or task.
3. **Parallel forks multiply startup costs.** Each fork has its own context cache and its own containers. N forks can mean N copies of every context. **Check**: with `forkCount`/`maxParallelForks` > 1, the context-start count grows with N. **Fix**: fix check 1 first, then size forks to the cores (`test-parallelism.md` §1.1). In-JVM JUnit parallel execution shares the cache, at the price of thread-safety. **Gain**: measure both shapes (heuristic). **Risk**: memory: forks × heap must fit the runner.
4. **A container per test class.** **Fact**: the singleton pattern starts a container once "for several test classes": a `static final` container started in a static block of a shared base class; the Ryuk container stops it when the JVM exits ([Testcontainers](https://java.testcontainers.org/test_framework_integration/manual_lifecycle_control/)). **Check**: more container starts than distinct images; `@Container` on non-shared fields; `@Testcontainers` on every class. **Fix**: the singleton base class, with one database or schema per fork (`test-parallelism.md` §5). `withReuse(true)` targets developer machines; on a fresh CI runner nothing survives to be reused (heuristic). **Gain**: one container start per class removed (heuristic). **Risk**: tests now share a container, so they must clean up their data.
5. **Unit and integration tests in one serial step.** **Check**: one test task or Surefire execution runs both, and the slow classes are all integration tests. **Fix**: split them (Surefire for unit, Failsafe for integration; Gradle test suites) into parallel jobs, so the critical path is the slower of the two rather than their sum. **Gain**: the shorter suite's duration, minus one job setup (heuristic). **Risk**: more billed minutes (`build-steps.md` §8). Both jobs stay required.
6. **Real waits.** **Check**: the `Thread.sleep` count in `src/test`, and tests whose duration is a round multiple of a second. **Fix**: poll with a timeout (Awaitility), or inject a clock. **Gain**: the summed sleep time (arithmetic). **Risk**: none.
7. **Context does more work than the test needs.** **Check**: `@SpringBootTest` on tests that exercise one controller or repository. **Fix**: a test slice (`@WebMvcTest`, `@DataJpaTest`) starts fewer beans, and `spring.main.lazy-initialization=true` in the test profile defers beans the test never touches. **Gain**: read the new startup seconds from the log (heuristic). **Risk**: every distinct slice is another cached context (check 1), so measure the suite total, not one class. Lazy initialization hides wiring errors; keep one full-context test without it.

## Cache paths
None on disk. The caches here live inside the test JVM (Spring contexts, started containers), which is why fork settings decide whether they work.

## Version traps
- **Spring Boot**: `@MockBean`/`@SpyBean` are deprecated since Boot 3.4 in favour of Spring Framework's `@MockitoBean`/`@MockitoSpyBean`. Both kinds are part of the context cache key.
- **Surefire 3.6**: the old `forkMode` values named in the Spring docs map to `forkCount`/`reuseForks`; several parallel settings are ignored (`test-parallelism.md` §8).
- **JUnit 6**: parallel execution is off by default (`test-parallelism.md` §8).
