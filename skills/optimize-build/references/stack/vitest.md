# vitest — optimize-build stack reference

Use when: detect-stack.sh reported `vitest`. Lanes: test, cache.

**Versions.** Checked 2026-11-09, re-verified 2026-11-18. The latest is **5.1.1** (5.1.0 shipped 2026-11-02). Maintained lines: 4.1.12 and 3.2.7 (`npm view vitest dist-tags`). Read the repo's version first with `npm ls vitest vite jsdom happy-dom @vitest/coverage-v8`, because most knobs here changed in 4.0 or 5.0.

**(local)** marks a run on 2026-11-09 against vitest 5.1.0 (Node 26.13, npm 11.20) on a small fixture. It proves behaviour, not gains.

**Elsewhere.** Workers, blockers and shuffling in general: `test-parallelism.md`. DOM, CSS and import cost in general: `test-environment.md`.

## Measure

### 1. `Duration` line in the CI log

Extract it with `perl -pe 's/\e\[[0-9;]*m//g' job.log | grep -E '(^| )(Test Files|Duration|Per blob) +[0-9]'`. The format depends on the version. Checked in the published dists (3.2.7, 4.0.0–4.0.18 bisected, 4.1.0, 4.1.12, 5.1.0):

| Version | Format |
|---|---|
| 3.2 – 4.0.13 | Absolute times: `transform, setup, collect, tests, environment, prepare` |
| 4.0.14 – 4.1.x | Absolute times: `transform, setup, import, tests, environment` |
| 5.0+ | Percentages, e.g. `Duration 39.42s (tests 48%, environment 20%, import 11%, typecheck 6%, transform 6%, worker 6%, setup 5%)` |

- **Units.** Absolute times are sums across workers, so they can exceed wall time. v5 percentages are shares of **summed per-worker phase time, not wall time**. They are sorted, and phases under 0.5% are dropped ([durationBreakdown.ts](https://github.com/vitest-dev/vitest/blob/v5.1.0/packages/vitest/src/node/reporters/durationBreakdown.ts)).
- **v5 phases** ([perf guide](https://vitest.dev/guide/improving-performance)): `environment`: creating jsdom or happy-dom, per file. `worker`: setting up the runner and mocks. This is the old `prepare`, and isolation pays it once per file. `transform`: waiting on Vite to resolve and transform modules. `import`: evaluating the file's module graph and collecting tests. `setup`: running `setupFiles`. `tests`: test bodies and hooks. If this dominates, there is "little to gain from configuration changes". `typecheck`: `--typecheck`.
- **Route by the top phase.** environment/worker → checks 5–7. CSS → 8–9. transform/import → 9–12. setup → 13. typecheck → 14. tests → 2–4, 16–17.
- **Trap: [#11807](https://github.com/vitest-dev/vitest/issues/11807) (open).** With `isolate: false`, a worker's one-time environment setup is counted once per file. That inflates `environment` to about 99%.
- **Per-file phases.** v5 logs no absolute per-phase seconds. Use a reporter on `TestModule.diagnostic()`, which exposes `environmentSetupDuration`, `prepareDuration`, `setupDuration`, `collectDuration` and `duration`. v5 also adds `concurrencyId`, which is at most maxWorkers ([TestModule](https://vitest.dev/api/advanced/test-module)). Example: the `SlowFiles` reporter in `test-environment.md` §1.

### 2. Hints (5.0+)

- `experimental.diagnostics` is on by default, in CI too. It prints at most one kind of hint after the summary (one per qualifying project), checking environment, then import, then transform, then falling back to isolate. No hints in watch mode or on `--merge-reports` output, so read them in each shard's log (5.1.0 dist).
- It never suggests changing an option that is set explicitly ([experimental](https://vitest.dev/config/experimental)).
- Example hints. Environment: "create it once per worker with pool: 'vmThreads' (keeps per-file isolation) or isolate: false". Import: "837 modules were evaluated 16740 times". Transform: tells you to persist the cache dir in CI.

### 3. Reporters ([reporters](https://vitest.dev/guide/reporters))

- **Passing any `--reporter` replaces the defaults.** The defaults are `default`, or `minimal` when an AI agent is detected, plus `github-actions` when `GITHUB_ACTIONS=true`. Add `--reporter=default`, or spread `configDefaults.reporters`. `--reporter=blob` alone prints no summary and no Duration line (local). `minimal` still printed the summary and Duration line (local), although the docs say it suppresses the summary.
- **Output locations.** `json`: Jest-compatible, with per-file `testResults[].startTime/endTime`. v5 writes it to `.vitest/json/output.json`. v4 and earlier write it to stdout. `junit`: `.vitest/junit/output.xml`. `html`: `.vitest/index.html` (set with `outputDir`). An explicit `outputFile` wins. `[['json', { stdout: true }]]` restores stdout output.
- **One single-string `--outputFile=path` with two file reporters** writes both to that path, and the second clobbers the first (local). Use one flag per reporter instead: `--outputFile.junit=reports/junit.xml --outputFile.json=reports/r.json` ([outputFile](https://vitest.dev/config/outputfile)).
- **The json per-file span** runs from the first test start to the last test end, so it **excludes environment and import** ([json.ts](https://github.com/vitest-dev/vitest/blob/v5.1.0/packages/vitest/src/node/reporters/json.ts)). Rank files with it only when `tests` dominates.

### 4. Imports

- **4.1+:** `npx vitest run --experimental.importDurations.print` lists the top 10 imports with Self and Total time. Thresholds: warn 100 ms, danger 500 ms. It prints only with the `default`, `verbose` or `tree` reporter. `--experimental.importDurations.failOnDanger` turns it into a CI budget.
- **5.1.0:** pass the bare flag. `…print=true` printed nothing (local).
- **4.0.15–4.0.18:** use `--experimental.printImportBreakdown` instead.

### 5. `vitest doctor [filters]` (5.0+)

Doctor measures alternative configs instead of estimating them ([CLI](https://vitest.dev/guide/cli#vitest-doctor), [PR #10710](https://github.com/vitest-dev/vitest/pull/10710)).

- **Needs a green, stable suite.** Otherwise it prints "doctor needs a green suite" and exits 1.
- **What it runs.** The baseline at least twice, then each candidate: `pool: 'threads'`; `vmThreads` and `vmForks` (DOM or custom environments); `isolate: false`, checked with a shuffled file order (on failure: "tests depend on isolation"); `happy-dom` for jsdom projects if installed; `fsModuleCache` if it is off. It then halves `maxWorkers` on top of the winner while each step gains at least 5%.
- **What it recommends.** Only candidates **at least 10% faster** than the baseline. Among candidates within 5% of the fastest, it prefers one that keeps isolation.
- **Cost.** 3, 2 or 1 reps for suites under 10 s, under 60 s, or longer (5.1.0 dist). That totals roughly (candidates + 2) × suite time, so run it locally or in a one-off job.
- **Output.** A config snippet. On the docs fixture the forks baseline took 4.08 s. `threads` was −11%, `vmThreads` 1.33 s (−67%), and `isolate: false` 1.28 s (−69%). On the local fixture, `threads` was −12%.

### 6. Shards

- **Per-shard time.** `vitest run --merge-reports` prints `Per blob  121ms 205ms`: the execution time of each shard. Use it as a balance check (local). The line is also in the 3.2.7 and 4.0.18 dists.
- **Preview (5.1.1+).** `vitest list --filesOnly --shard=1/4 --json` lists a shard's files without running them (local, 5.1.1). Through 5.1.0, `--filesOnly` ignores `--shard` and lists every file ([#11846](https://github.com/vitest-dev/vitest/pull/11846)). Join that with per-file durations to estimate balance.

### 7. Profiles ([profiling](https://vitest.dev/guide/profiling-test-performance))

- **v4+:** set top-level `execArgv: ['--cpu-prof','--cpu-prof-dir=.prof']` with `fileParallelism: false`. In v3 this was `poolOptions.<pool>.execArgv`.
- **Main thread:** `node --cpu-prof ./node_modules/vitest/vitest.mjs --run`.

## Checks

1. **Dead v3 options after an upgrade.** **Check** on 4.0 or later, `rg -n 'poolOptions|single(Fork|Thread)|max(Threads|Forks)|minWorkers|VITEST_MAX_(THREADS|FORKS)|memoryLimit|environmentMatchGlobs|poolMatchGlobs|vitest\.workspace' -g '!node_modules' .`. → **Good** no hits. → **Fix** map each hit to `maxWorkers`, a top-level `isolate`/`execArgv`/`vmMemoryLimit`, or `projects`. Serialise via check 2. → **Gain** correctness. v4+ only logs a deprecation for `poolOptions` and ignores it ([resolveConfig.ts](https://github.com/vitest-dev/vitest/blob/v5.1.0/packages/vitest/src/node/config/resolveConfig.ts)). So a `singleFork: true` silently stops serialising, which makes DB tests collide. A tuned `maxForks` falls back to n−1. → **Risk** none.
2. **A whole-suite serialiser.** **Check** `rg -n "fileParallelism['\"]?\s*:\s*false|--no-file-parallelism|maxWorkers['\"]?\s*[:=]\s*['\"]?1\b|VITEST_MAX_WORKERS=1" .`. `fileParallelism: false` forces `maxWorkers = 1`, overriding the user value (resolveConfig.ts). → **Good** the serialiser is set only on a serial-lane project. → **Fix** use the snippet below. Gate the change with shuffled, repeated runs: `--sequence.shuffle.files --sequence.shuffle.tests --sequence.seed=$s --repeats=N` (5.0+). → **Gain** up to workers× on `tests`. **None on 2-vCPU runners**, where the default is already 1 worker. → **Risk** a shared DB, ports or paths. Key per-worker resources on `VITEST_POOL_ID` (1..maxWorkers), never on `VITEST_WORKER_ID`, which is unbounded.
   ```ts
   import { configDefaults, defineConfig } from 'vitest/config'   // v4+: serial lane runs after the parallel group
   export default defineConfig({ test: { projects: [
     { extends: true, test: { name: 'par', exclude: [...configDefaults.exclude, '**/*.serial.test.ts'] } },
     { extends: true, test: { name: 'serial', include: ['**/*.serial.test.ts'], fileParallelism: false, sequence: { groupOrder: 1 } } },
   ] } })
   ```
   **Pitfall** inherited arrays are **concatenated** ([projects](https://vitest.dev/guide/projects)). If the root sets `test.include`, the serial lane runs every root file too. Fix: move `include` into each project, or use `extends: false`. **Order** projects with the same `groupOrder` run together, and lower groups run first ([sequence](https://vitest.dev/config/sequence#sequence-grouporder)).
3. **Worker count.** **Check** the default is `max(n−1,1)`, or `max(⌊n/2⌋,1)` in watch mode, where n = `os.availableParallelism()` ([workers.ts](https://github.com/vitest-dev/vitest/blob/v5.1.0/packages/vitest/src/utils/workers.ts)). The [docs](https://vitest.dev/config/maxworkers) say "all available parallelism", which is imprecise. `%` values are rounded and clamped to [1, n]. The `VITEST_MAX_WORKERS` env var overrides the config. Since 5.0, `--maxWorkers` reaches projects. → **Good** in a container with a CPU quota, `maxWorkers` equals the quota. Under turbo or nx, only one layer runs parallel. → **Fix** set `maxWorkers` explicitly. More workers is not always faster: they all share one main-thread Vite server, and `doctor` probes this. On a big machine, run local shards instead. For example, on 32 CPUs run 4 shards with `VITEST_MAX_WORKERS=7` each, then `--merge-reports` (perf guide). → **Gain** typical, unmeasured. → **Risk** none.
4. **In-file concurrency.** **Check** I/O-bound files (network mocks, DB, timers) whose tests run serially. → **Good** I/O-bound tests are marked concurrent. → **Fix** use `test.concurrent`, `describe.concurrent` or `sequence.concurrent`. These are capped by `maxConcurrency` (default 5). Snapshots must use the context `expect`: `async ({ expect }) => …` ([test API](https://vitest.dev/api/test)). v5 removed `test.sequential`; use `{ concurrent: false }`. → **Gain** only for I/O-bound tests; unmeasured. → **Risk** shared module state. Fake timers patch the worker's globals.
5. **Pool.** **Check** `rg -n "pool\s*:" -g 'vitest.config.*' -g 'vite.config.*' -g '!node_modules' .`. The default has been `forks` since 2.0 ([v2 migration](https://v2.vitest.dev/guide/migration)). → **Good** the pool `vitest doctor` picked. → **Fix** `pool: 'threads'`. The docs say forks "may be slightly slower than `pool: 'threads'` in larger projects" ([perf guide](https://vitest.dev/guide/improving-performance#pool)). → **Gain** −11% on the docs fixture, −12% local. → **Risk** under `threads`, `process.chdir()` is unavailable, `process.env.TZ` changes are ignored, and native modules (Prisma, bcrypt, canvas) can segfault.
6. **The environment is recreated for every file.** **Check** `environment` or `worker` tops the Duration line, under `isolate: true` with a DOM environment. → **Good** the environment is built once per worker, or few files use a DOM. → **Fix** either (a) `pool: 'vmThreads'` or `'vmForks'`: each file gets a fresh context, but the environment is built once per worker. [`isolate`](https://vitest.dev/config/isolate) has no effect there: "This option has no effect on `vmThreads` and `vmForks` pools". Prefer `vmForks` on large suites, because recycling it is much cheaper. Or (b) `isolate: false`: the perf guide says "Prefer `isolate: false` with `threads` if the tests tolerate shared state: it is the fastest option". Set it per project, for safe files only. React Testing Library's auto-cleanup then needs `globals: true`; otherwise call `afterEach(cleanup)` ([RTL](https://testing-library.com/docs/react-testing-library/api#cleanup)). → **Gain** −67% / −69% on the doctor fixture. → **Risk** vm pools: `instanceof Error` is false for errors from native modules, `toStrictEqual` hits prototype mismatches, ESM leaks need `vmMemoryLimit` recycling, and global access is slower. `isolate: false`: state and mocks leak across files.
7. **DOM environment on pure-logic files.** **Check** the global `environment` is `'jsdom'` or `'happy-dom'`, and `git ls-files '*.test.ts' | xargs grep -LE "render|screen\.|document|window|@testing-library"` lists files that never touch the DOM. → **Good** pure-logic files run in `node`. → **Fix** split with `projects`, one `include` per environment. Or mark single files with `// @vitest-environment node`; `@jest-environment` docblocks are parsed too (already in 3.2.7 and 4.x). `environmentMatchGlobs` was removed in 4.0. → **Gain** one environment import saved per moved file: jsdom "roughly 200-500ms", happy-dom "90-200ms" (perf guide). `doctor` also tries a happy-dom swap. → **Risk** files that reach `window` indirectly fail in `node`.
8. **CSS processing.** **Check** `rg -n "css\s*:" -g 'vitest.config.*' -g 'vite.config.*' -g '!node_modules' .` finds `css: true` or `include: [/.+/]`, but `rg -n "toHaveStyle|getComputedStyle" .` finds no style assertions. The default is `{ include: [] }` ([css](https://vitest.dev/config/css)). The `vitest:css-disable` plugin (`enforce: 'pre'`) returns `''` for `.css|less|sass|scss|styl|stylus|pcss|postcss`. CSS Modules become a proxy with `stable` names (`_foo_<hash>`). With `css: true`, a real `<style>` is appended (local: 0 tags by default, 1 with it). Browser mode always sets `css = true` (5.x). → **Good** the default, or a narrow `include` only where styles are asserted. → **Fix** remove the setting, or narrow `include`. → **Gain** ByRole 18–120× faster with 5k rules removed (local micro-benchmark, `test-environment.md` §3). → **Risk** style assertions. Runtime CSS-in-JS injects its styles regardless.
9. **Plugins inherited from vite.config.** **Check** `rg -n "tailwind|postcss|sass|checker|pwa|svgr" vite.config.*`, when Vitest inherits `vite.config` (via a `test` key, `mergeConfig`, or v5 `extends: true`). `enforce: 'pre'` plugins run before `vitest:css-disable` (local). → **Good** test runs load only the framework plugin and aliases. → **Fix** gate plugins: `plugins: [react(), !process.env.VITEST && tailwindcss()]`. Vitest sets `VITEST=true` before loading the config, and `mode` is `'test'`. Or use a standalone `vitest.config.ts`. → **Gain** typical, unmeasured. → **Risk** tests that need the plugin's output.
10. **Projects with their own Vite server (5.0+).** **Check** `DEBUG=vitest:projects npx vitest run` prints "creating a Vite server for project". A project gets its own server when it sets `plugins`/`resolve`, `alias`, `browser`, `css`, `deps.moduleDirectories`, `deps.optimizer`, `mode` or `root`. So do `extends: false` projects and config-file projects. → **Good** inline projects share one server (`sharedViteServer`, default `true`, [docs](https://vitest.dev/config/sharedviteserver)). → **Fix** hoist shared plugins and aliases to the root. `environment`, `setupFiles`, `env` and `server.deps` keep sharing. → **Gain** shared files are transformed once instead of once per project; unmeasured. → **Risk** a plugin's `config` hook can't see per-project options.
11. **Module cache off or cold.** **Check** the version, plus `rg -n 'fsModuleCache|VITEST_FS_MODULE_CACHE' .` (5.1.1 adds the `VITEST_FS_MODULE_CACHE` and `VITEST_FS_MODULE_CACHE_PATH` env vars; config and CLI take priority). The cache is on from 5.0.4. It was off in 5.0.0–5.0.3, and in 4.x it is `experimental.fsModuleCache` (4.0.11+). In CI, `DEBUG=vitest:cache:fs` logs `[read]`, `[empty]` and `[write]`. → **Good** `[read]` lines appear in CI. → **Fix** enable and persist the cache (see Cache paths). → **Gain** in the docs, a 900-module file went from 8.75 s to 5.90 s on the second run. On full suites, "parallelization already mitigates the cost" ([perf guide](https://vitest.dev/guide/improving-performance#caching-between-reruns)). The CI gain is unmeasured. → **Risk** plugins that read external state go stale. Use `defineCacheKeyGenerator`, or turn the cache off. It has no effect in browser mode.
12. **Barrels and heavy imports.** **Check** a high `import` share, the import hint, or `importDurations` output. → **Good** no import over `thresholds.danger` (500 ms). → **Fix** use deep imports. Or pre-bundle with `deps.optimizer.client` (jsdom/happy-dom) or `.ssr` (node), e.g. `{ enabled: true, include: ['@mui/icons-material'] }`. This is off by default. `web` was renamed `client` in 4.0 ([deps](https://vitest.dev/config/deps)). → **Gain** ~85% fewer transformed files in the docs example ([profiling](https://vitest.dev/guide/profiling-test-performance)). → **Risk** you can't edit `node_modules` while debugging.
13. **Heavy `setupFiles`.** **Check** the `setup` share. Setup files run "before each test file". Under `isolate: false` their imports stay cached, but "the setup file itself is executed again" ([setupFiles](https://vitest.dev/config/setupfiles)). → **Good** a small `setup` share. → **Fix** guard expensive work with a `globalThis` flag, scope the file to the project that needs it, and move one-time work to `globalSetup` with `provide`/`inject`. → **Gain** typical, unmeasured. → **Risk** `globalSetup` runs in the main process, so it can't share in-memory objects with tests.
14. **Typecheck in the test step.** **Check** `rg -n typecheck .` finds it in the config or scripts, or the Duration line shows a `typecheck` share. → **Good** type checking runs once, in its own job. → **Fix** drop `--typecheck` in CI if a `tsc --noEmit` job covers the `*.test-d.ts` files. → **Gain** that share. → **Risk** type tests end up unchecked.
15. **Coverage on every PR.** **Check** `--coverage` or `coverage.enabled`, and which provider. `v8` is the default. Istanbul is "slower than V8 due to instrumentation overhead", though V8 "can be slower… when loading lots of different modules" ([coverage](https://vitest.dev/guide/coverage)). → **Good** `v8`, and coverage only where it gates. → **Fix** use `v8`. With shards, run `--reporter=blob --coverage`, then `--merge-reports --coverage`. → **Gain** unmeasured. → **Risk** coverage gates.
16. **Sharding.** **Check** `rg -n -- '--shard' .`. `--shard` throws in watch mode, so use `vitest run`. Files are split **by count**, after sorting by the sha1 of the relative path. Durations are ignored ([BaseSequencer.ts](https://github.com/vitest-dev/vitest/blob/v5.1.0/packages/vitest/src/node/sequencers/BaseSequencer.ts)). Since 4.0, the leftover files are spread evenly. → **Good** in `Per blob`, max/mean ≤ ~1.3 (heuristic). → **Fix** run `--reporter=default --reporter=blob --shard=${{ matrix.i }}/${{ matrix.n }}`, then upload `.vitest` (v4 and earlier: `.vitest-reports`) with `include-hidden-files: true`. In the merge job, set `if: ${{ !cancelled() }}`, download with `merge-multiple: true` into `.vitest`, and run `npx vitest --merge-reports`. Set `VITEST_BLOB_LABEL=<os>` for multi-OS runs ([sharding](https://vitest.dev/guide/improving-performance#sharding)). If shards are unbalanced, split giant files or write a `sequence.sequencer` that overrides `shard()`. → **Gain** up to N× on the test step, minus N × setup. → **Risk** per-job setup and billing rounding (`test-parallelism.md` §7).
17. **Cold results cache.** **Check** CI never restores `node_modules/.vite/vitest`. The sequencer runs failed files first, then the longest by cached duration. Files with no cached result run largest file first, so a cold run never orders by duration. → **Good** `results.json` restored, so slow files start first. → **Fix** cache it (see Cache paths). → **Gain** a shorter tail; typical, unmeasured. → **Risk** none. `sequence.shuffle` ignores this order.
18. **Test selection (optional).** **Check** PR runs always run the full suite. Options: `--changed [since]`; 5.1 adds `experimental.recordDependencies`, `--sinceLastRun` and `--last-failed`. → **Good** selection on PRs only, full suite elsewhere. → **Fix** `vitest run --changed origin/main` on `pull_request` (the base ref must be fetched; the default checkout depth is 1). → **Gain** proportional to the files skipped. → **Risk** guardrail 1 applies: never skip the full suite on main, in the merge queue or for a release. Selection also misses dependencies that aren't imports, such as fixtures read through `fs`.

## Cache paths

| Cache | Path | Key | Restore / notes |
|---|---|---|---|
| fs module cache | `node_modules/.vitest-cache`, set with `fsModuleCachePath` ([docs](https://vitest.dev/config/fsmodulecachepath)). v4 (experimental): `node_modules/.experimental-vitest-cache` | `vitest-fsm-${{ runner.os }}-${{ hashFiles('<lockfile>') }}-${{ github.sha }}`, restore-keys `vitest-fsm-${{ runner.os }}-${{ hashFiles('<lockfile>') }}-` | Restore **after** install, because `npm ci` deletes `node_modules`. Or move `fsModuleCachePath` outside it. One dir serves all projects. `vitest --clearCache` wipes it. |
| results (test ordering, `--last-failed`, `recordDependencies` → `dependencies.json`) | `<Vite cacheDir>/vitest/<hash>/results.json`, by default under `node_modules/.vite/vitest/`. Find it with `find node_modules/.vite -name results.json` (local). | `vitest-results-${{ runner.os }}-${{ github.sha }}` + prefix restore | Restore after install, or set Vite `cacheDir` outside `node_modules`. `cache.dir` "has no effect"; set Vite `cacheDir` instead ([cache](https://vitest.dev/config/cache)). Its shape changed in 5.0.4, so v4 entries aren't reused. |
| V8 compile cache | `NODE_COMPILE_CACHE=node_modules/.cache/node-compile-cache` (docs example) | OS + Node version + lockfile | Use only if the dir persists, since the first run pays for serialization. Vitest turns it off in workers under v8 coverage. `NODE_DISABLE_COMPILE_CACHE=1` takes precedence (perf guide). |
| Reports (not caches) | `.vitest/{blob,json,junit,attachments}/`, `.vitest/index.html` (v5) | — | Upload as artifacts. Never put them in `actions/cache`. |

**How the fs cache invalidates itself** (5.1.0 dist `getLockfileHash`, which comes from Vite):
- **Hash input.** Vitest takes the sha256 of the **installed** lockfile. It walks up from the root and uses the first one it finds: npm `node_modules/.package-lock.json`; pnpm `node_modules/.pnpm/lock.yaml`; yarn `node_modules/.yarn-state.yml`, `.yarn-integrity` or `.pnp.cjs`; bun `bun.lock(b)`. For npm, Yarn 1 and bun, if `patches/` exists (`.yarn/patches` under Yarn PnP), its **mtime** is added to the hash; pnpm and Yarn `node_modules` (`.yarn-state.yml`) installs skip this.
- **On mismatch** the whole cache is wiped, and Vitest logs `fs cache was cleared because lockfile has changed`.
- **Per-entry keys** cover content, module id, the Vite environment config and coverage status. Plugin options are not tracked. Since 5.1, the deps optimizer is part of the key too.
- **Local tests** (npm 11.20). Built after `npm ci` and restored after a fresh `npm ci`: `[read]` hits. Built after the `npm install` that wrote the lockfile and restored after `npm ci`: cleared, because the hidden lockfile differed (on macOS, one optional `fsevents` entry). Built after `npm install` from the existing lockfile and restored after `npm ci`: `[read]` hits, the hidden lockfile is byte-identical. So build the cache in CI, from the committed lockfile.
- **Untested, inferred from source.** A committed `patches/` dir (patch-package) gets a new mtime on every checkout, so the cache would clear on every run. A likely fix is pinning its mtime before Vitest runs: `touch -t 200001010000 patches`.

## Version traps

| Version | Change and trap |
|---|---|
| 2.0 | The default `pool` became `forks`. |
| 3.2 | `workspace` deprecated in favour of `projects` ([v3 projects](https://v3.vitest.dev/guide/projects)). |
| 4.0 (2025-10-22) | **Requirements:** Node ≥20, Vite ≥6. Tinypool removed.<br>**Pool options:** `maxThreads`/`maxForks` → `maxWorkers`. `VITEST_MAX_THREADS/FORKS` → `VITEST_MAX_WORKERS`. `singleThread`/`singleFork` → `maxWorkers: 1, isolate: false`. `poolOptions.*` moved to the top level; any leftover `poolOptions` is now **ignored**, with only a deprecation log. `minWorkers` removed. `memoryLimit` → `vmMemoryLimit`.<br>**Projects:** `isolate`, `fileParallelism` and `execArgv` can be set per project. The `workspace` file must move into `projects`.<br>**Removed:** `environmentMatchGlobs`/`poolMatchGlobs`, `coverage.all`, and the `basic` reporter (now `default` with `summary: false`).<br>**Renamed:** `deps.optimizer.web` → `client`. `verbose` now prints a flat list; the old output is `tree`.<br>Shards are spread more evenly ([v4 migration](https://v4.vitest.dev/guide/migration), [v4.0.0](https://github.com/vitest-dev/vitest/releases/tag/v4.0.0)). |
