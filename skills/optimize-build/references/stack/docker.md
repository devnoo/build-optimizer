# docker — optimize-build stack reference
Use when: detect-stack.sh reported `docker`. Lanes: docker, cache.

Checked 2026-11-09 against docs.docker.com, the Dockerfile reference at `dockerfile/1.28.0`, and release pages. **Verified locally** = run on Docker Engine 29.8.2 / Buildx 0.37.2 / Compose 5.5.0 (OrbStack). Latest that day: build-push-action v7.4.0, setup-buildx-action v4.4.1, setup-qemu-action v4.4.0, bake-action v7.5.0, docker/github-builder v1.19.0 (`@v1`), Buildx 0.38.2, BuildKit 0.34.2, Dockerfile frontend 1.28.0, buildkit-cache-dance v3.4.0.

## Measure
Find the build step in the CI timings first (`ci-github-timings.md`). Then go per instruction. Always compare three cases: **cold** (`--no-cache`, or a fresh hosted runner with no `cache-from`), **source-only change** (the usual PR), and **lockfile change**. Only the source-only case should be fast.
- **CI log.** In a non-TTY session, `--progress=auto` (the default) picks `plain` ([buildx build](https://docs.docker.com/reference/cli/docker/buildx/build/)). Every vertex prints `#N <name>`, followed by `#N DONE 12.3s` or `#N CACHED`. To rank vertices (verified locally on plain output with GH timestamp prefixes):
  ```bash
  gh api --allow-escape-sequences repos/O/R/actions/jobs/$JOB/logs > job.log   # several builds in one job reuse #N, so fetch per step
  perl -ne 's/^\S+Z //; next unless /^#(\d+) (.+)$/; my ($i,$t)=($1,$2); $n{$i}//=$t;
    print "$1s\t$n{$i}\n" if $t=~/^DONE ([\d.]+)s/; print "CACHED\t$n{$i}\n" if $t eq "CACHED"' job.log | sort -t$'\t' -k1 -rn | head -20
  ```
  Vertices to read:
  - `[stage i/n] RUN …`: the work itself. On a source-only change, the install RUN must say `CACHED`.
  - `[internal] load build context` + `transferring context: 20.01MB 0.1s`: context size.
  - `importing cache manifest from …`: cache import (string from BuildKit `solver/llbsolver/bridge.go`).
  - `exporting to GitHub Actions Cache` / `exporting cache to registry`: the cost of cache export (BuildKit exporter `Name()`).
  - `exporting to image`: the image export, plus pushing.
- **Local per-vertex timing** (verified locally): `docker buildx build --progress=rawjson . 2> build.json`, then:
  ```jq
  # jq -rs -f steps.jq build.json
  def ts: capture("^(?<b>[^.Z]+)(\\.(?<f>[0-9]+))?Z$") | (.b + "Z" | fromdate) + ("0." + (.f // "0") | tonumber);
  [.[] | .vertexes[]? | select(.started and .completed)] | group_by(.digest)
  | map({n: .[0].name, c: any(.[]; .cached == true), s: ((map(.completed|ts)|max) - (map(.started|ts)|min))})
  | sort_by(-.s)[:20][] | "\(.s*10|round/10)s\t\(if .c then "CACHED" else "-" end)\t\(.n)"
  ```
- **Build history** (Buildx ≥0.20; `--format json` ≥0.21). `docker buildx history ls`, then `docker buildx history inspect [^N]` prints `Build Steps: 16/16 (25% cached)`. The JSON gives `NumCachedSteps`, `NumTotalSteps` and `Duration` in ns ([inspect](https://docs.docker.com/reference/cli/docker/buildx/history/inspect/), [buildx releases](https://github.com/docker/buildx/releases)).
- **build-push-action/bake-action v7 job summary**: shows the Dockerfile, the build duration and cache utilization. It also uploads a build record artifact that Docker Desktop can import. The summary is GitHub.com only, not GHES ([build summary](https://docs.docker.com/build/ci/github-actions/build-summary/)).
- **Persistent/self-hosted builders**: `docker buildx du` shows builder cache size.

## Checks
Detect: `find . \( -name 'Dockerfile*' -o -name '*.Dockerfile' -o -name Containerfile \) -not -path '*/node_modules/*'; ls .dockerignore *.dockerignore`
`grep -nE 'build-push-action|bake-action|github-builder|setup-buildx|setup-qemu|cache-(from|to)|platforms:|push:|load:|docker (buildx )?(build|bake)|compose.*build' .github/workflows/*.y*ml`
`grep -nE '^(FROM|ARG|COPY|ADD)|--mount=type=|^RUN .*\b(ci|install|fetch|download|restore)\b' Dockerfile*`

1. **Layer order.** **Check**: a `COPY . .` (or `ADD .`) line comes before the install RUN. **Good**: only manifests and the lockfile are copied or bound before install, and the source is copied after it. "Steps that change often should appear near the end" ([optimize](https://docs.docker.com/build/cache/optimize/)). **Fix**: `COPY package.json package-lock.json ./` → `RUN npm ci` → `COPY . .`. **Gain**: a source-only change skips install, often minutes (typical, unmeasured). Confirm with the install vertex showing `CACHED`. **Risk**: install may need more than the manifests: `.npmrc`, `patches/`, workspace `package.json` files, postinstall inputs.
2. **Bind-mount manifests into the install RUN** (Dockerfile ≥1.2). **Check**: `COPY package*.json` used only to feed a read-only install. **Fix**: `RUN --mount=type=bind,source=package.json,target=package.json --mount=type=bind,source=package-lock.json,target=package-lock.json --mount=type=cache,target=/root/.npm npm ci`. **Verified locally**: changing the bound file's content re-runs the RUN, and a `touch` alone stays `CACHED` (mtime is not in the checksum, [invalidation](https://docs.docker.com/build/cache/invalidation/)). **Gain**: one layer fewer, and the manifests never enter the image (typical, unmeasured, small). **Risk**: binds are read-only, and with `rw` any writes are discarded. Use this only for installs that do not write the manifest (`npm ci`, `pip install -r`, `go mod download`). For monorepos with many workspace manifests, use check 11.
3. **Cache mounts, and whether CI keeps them.** **Check**: `grep -n 'type=cache' Dockerfile*` and `grep -n buildkit-cache-dance .github/workflows/*`. **Facts**: cache mounts live in the builder's local storage. They "are not included in exported build cache (`--cache-to`), and are not restored by `--cache-from`", so on fresh CI machines "cache mounts start empty on every build" ([Dockerfile ref](https://docs.docker.com/reference/dockerfile/#run---mounttypecache)). On persistent builders, the default GC prunes cache mounts unused for >48 h ([GC](https://docs.docker.com/build/cache/garbage-collection/)). **Good** on hosted runners: rely on the layer cache (check 4). The install layer is then `CACHED` whenever the lockfile is unchanged, so a cache mount only pays off on lockfile-change builds (heuristic). Persist it only if those builds are frequent (Renovate etc.). **Fix**: `reproducible-containers/buildkit-cache-dance@v3` between `actions/cache` (keyed on the lockfile hash) and the build, with `cache-map` (or `cache-dir` + `dockerfile`) and `skip-extraction: ${{ steps.cache.outputs.cache-hit }}` ([README](https://github.com/reproducible-containers/buildkit-cache-dance)). For pnpm without mounts: `pnpm fetch` (lockfile only) then `pnpm install --offline --frozen-lockfile` ([pnpm docker](https://pnpm.io/docker)). **Gain**: the download share of install, on lockfile-change builds only (typical, unmeasured). **Risk**: inject plus extract plus `actions/cache` save can cost more than it saves, so time those steps. Never let untrusted PRs write a store that trusted builds restore (pnpm docs).
4. **External layer cache exists and is shaped right.** **Check**: no `cache-from`, or `mode` unset on a multi-stage build, or several images sharing one `type=gha` without `scope=`. **Good**:
   ```yaml
   cache-from: type=gha,scope=api
   cache-to: ${{ github.event_name == 'push' && 'type=gha,mode=max,scope=api' || '' }}   # one scope per image; write from main only
   ```
   `mode` defaults to `min`: "only layers that are exported into the resulting image are cached". `max` caches "all layers … even those of intermediate steps", so a builder stage's install layer survives only with `max` ([backends](https://docs.docker.com/build/cache/backends/)). The default `scope` is `buildkit`, and builds sharing a scope overwrite each other ([gha](https://docs.docker.com/build/cache/backends/gha/)). **Gain**: unchanged layers become `CACHED` on fresh runners (typical, unmeasured). Read the `exporting to …` vertex for the cost. **Risk**: `type=gha` shares the repo's 10 GB Actions cache, so a big `mode=max` evicts dependency caches (`ci-github-caching.md`). On low-trust triggers (`pull_request_target`, `issue_comment`) the export fails with `failed to reserve cache`. In that case omit `cache-to`, or add `ignore-error=true` ([GHA cache](https://docs.docker.com/build/ci/github-actions/cache/)).
5. **Pick the backend.** `gha`: still labelled "beta". It is rate-limited, `ghtoken` (a token with `repo` scope, set automatically by build-push-action from `github-token`) cuts API calls, and it reads only the current, base and default branch scopes. `registry`: `type=registry,ref=<img>:buildcache,mode=max`. It sits outside the Actions quota, and `ref` must not be "the same as the target location". Fork PRs have no push credentials ([registry](https://docs.docker.com/build/cache/backends/registry/)). `inline`: supports `min` only. `local` + `actions/cache`: grows on every export unless `reset=true` (Buildx ≥0.35.0). Prefer `registry` for large images or repos near quota.
6. **Driver supports cache export.** **Check**: `docker/setup-buildx-action` runs before the build. **Facts**: the default `docker` driver supports `gha`/`registry`/`local` cache only with the containerd image store ([backends](https://docs.docker.com/build/cache/backends/)). Otherwise buildx errors with `Cache export is not supported`. In Compose, unsupported `cache_from`/`cache_to` entries "are ignored", **silently** ([compose build](https://docs.docker.com/reference/compose-file/build/)), so confirm `importing cache manifest` shows up in the log.
7. **Context size / `.dockerignore`.** **Check**: no `.dockerignore`, or one that keeps `.git`, `node_modules`, `dist`, `coverage` or test output. Read the `transferring context:` size. **Facts**: the file sits at the context root. `<Dockerfile>.dockerignore` next to the Dockerfile takes precedence, `**` and `!` work, and the last matching line wins ([context](https://docs.docker.com/build/concepts/context/)). **Verified locally**: BuildKit sends only the paths that COPY/ADD reference. `COPY a.txt .` sent 38 B from a 20 MB context, while `COPY . .` sent 20.01 MB. So bloat costs time only with `COPY . .` or a bind of `.`, but then *any* stray changed file (logs, `.git`) also busts that layer. **Gain**: transfer time, "especially when using a remote builder", plus fewer cache busts (typical, unmeasured). **Risk**: excluding a file the build reads.
8. **Cache-busting args.** **Check**: `grep -nE '^ARG|SOURCE_DATE_EPOCH|build-args:|--build-arg' Dockerfile* .github/workflows/*`. **Facts**: a changed ARG misses "upon its first usage", and "all RUN instructions following an ARG" use it implicitly ([ARG caching](https://docs.docker.com/reference/dockerfile/#impact-on-build-caching)). A dynamic `SOURCE_DATE_EPOCH` "invalidates the cache for WORKDIR and all subsequent instructions" ([invalidation](https://docs.docker.com/build/cache/invalidation/)). **Fix**: declare `ARG GIT_SHA`/`BUILD_DATE` after install and build, in the final stage, or put them in labels via metadata-action. **Gain**: install and build are `CACHED` again on each commit (typical, unmeasured). **Risk**: none.
9. **Multi-stage + `--target`.** **Check**: `grep -nE '^FROM .* AS ' Dockerfile*`, plus `target:` in the workflow. **Facts**: "BuildKit only builds the stages that the target stage depends on". The legacy builder builds every stage up to `--target` ([multi-stage](https://docs.docker.com/build/building/multi-stage/)). **Good**: test and lint stages are separate, and only the jobs that need them build them with `--target`. The runtime stage copies artifacts only. **Gain**: skipped stages (typical, unmeasured). **Risk**: none.
10. **`COPY --link`** (Dockerfile ≥1.4). **Check**: `grep -nE '^COPY --from' Dockerfile* | grep -v -- --link`. **Fix**: `COPY --link --from=build /app/dist ./dist`, with a numeric `--chown=1001:1001`. **Gain**: performance is "equivalent or better" (cited). The layer is reused with `--cache-from` "even if the previous layers have changed", and a base-image bump can rebase without re-running the build ([COPY --link](https://docs.docker.com/reference/dockerfile/#copy---link)). **Risk**: it cannot follow symlinks in the destination, directory modes get overwritten, and named `--chown` fails.
11. **Monorepo slice.** **Check**: one global lockfile plus `COPY . .` before install in an app's Dockerfile. Any lockfile change "cascades into tens or hundreds of deploys" ([turbo docker](https://turborepo.dev/docs/guides/tools/docker)). **Fix**: a `prune` stage with `RUN turbo prune <app> --docker`, then `COPY --from=prune /app/out/json/ .`, then install, then `COPY --from=prune /app/out/full/ .`, then build. With `--docker`, the pruned lockfile and `.npmrc`/`.yarnrc.yml`/`bunfig.toml` are written into `out/json/` as well as `out/` (turbo source `crates/turborepo-prune`). For pnpm: `pnpm deploy --filter=<app> --prod <dir>` ([pnpm docker](https://pnpm.io/docker)). **Gain**: other apps' dependency changes no longer re-run this image's install (typical, unmeasured). **Risk**: the turbo version in the image must match the repo, and `globalDependencies` files are not copied unless `pruneIncludesGlobalFiles` is set ([prune](https://turborepo.dev/docs/reference/prune)). Pass `TURBO_TOKEN` with `RUN --mount=type=secret,id=TURBO_TOKEN,env=TURBO_TOKEN` (Dockerfile ≥1.10), not the guide's `ARG`/`ENV`.
12. **Multi-arch via QEMU.** **Check**: `setup-qemu-action`, or `platforms:` with several entries on one runner. **Facts**: QEMU "can be much slower than native builds", especially for "compilation and compression" ([multi-platform](https://docs.docker.com/build/building/multi-platform/)), and "Building multiple platforms on the same runner can significantly extend build times" ([GHA multi-platform](https://docs.docker.com/build/ci/github-actions/multi-platform/)). **Fix**: (a) `uses: docker/github-builder/.github/workflows/build.yml@v1`. `distribute` defaults to `true`, giving one platform per runner. **`cache` defaults to `false`**, so set `cache: true` and `cache-mode: max` ([github-builder](https://github.com/docker/github-builder)). (b) Cross-compile with `FROM --platform=$BUILDPLATFORM` when the toolchain can target `$TARGETPLATFORM`. **Gain**: large for compile-heavy builds, but there is no official multiplier, so measure (typical, unmeasured). **Risk**: arm runners need arm64 base images and native deps. github-builder requires GitHub-hosted Linux runners.
13. **PR waste.** **Check**: `push: true` on PRs, `load: true` in jobs that never run the image, `cache-to` on PRs, an image job with no path gate. **Fix**: `push: ${{ github.event_name != 'pull_request' }}`. Drop `load` unless the job runs the image. Write the cache from `main` only (check 4). Gate the job on Docker-relevant paths at job level (`build-steps.md` §8). `DOCKER_BUILD_RECORD_UPLOAD=false` skips the artifact upload ([README](https://github.com/docker/build-push-action)). **Gain**: seconds to whole jobs (typical, unmeasured). **Risk**: the action's default Git context ignores files that earlier steps changed, including `.dockerignore` processing. Use `context: .` after checkout when the build needs generated files.
14. **Several images.** **Check**: N sequential `docker build` steps or N build-push-action steps sharing base stages. **Fix**: one `docker buildx bake` (or `docker/bake-action@v7`) with a group. Bake "lets you run multiple builds concurrently with a single invocation" ([bake](https://docs.docker.com/build/bake/)). Compose ≥5.0 already builds through Bake. **Gain**: wall-clock ≈ the slowest image instead of the sum (typical, unmeasured). **Risk**: CPU and RAM contention on 2-vCPU runners.

## Cache paths
| Cache | Lives in | Key inputs | Restore order |
|---|---|---|---|
| Layer cache | builder-local; **empty on a fresh hosted runner** | instruction text + parent layer; COPY/ADD and bind sources: file checksum, **no mtime**; RUN: command string + ARG/ENV in scope | consulted per instruction; external caches are imported (`importing cache manifest`) before the first step |
| `type=gha` | Actions cache, one `buildkit-blob-1-sha256:…` entry per layer + `index-<scope>-1-…` ([gha.go](https://github.com/moby/buildkit/blob/master/cache/remotecache/gha/gha.go)) | `scope` (default `buildkit`), `mode` | inside the build step; readable from the current, base and default branch |
| `type=registry` | `<img>:buildcache` (≠ push tag); `image-manifest=true` by default | `ref`, `mode` | inside the build step; a missing ref fails the import only, and the build continues |
| `type=local` + `actions/cache` | `${{ runner.temp }}/.buildx-cache` | key `${{ runner.os }}-buildx-${{ github.sha }}`, restore-keys `${{ runner.os }}-buildx-` | `actions/cache` **before** the build; export with `mode=max,reset=true` |
| Cache mounts | builder-local; never in `--cache-to` | `id` (defaults to `target`); `sharing` defaults to `shared` (`locked` for apt) | with cache-dance: `actions/cache` restore → dance inject → build → dance extract (post) → save. Key on the lockfile hash |

Mount targets (Docker docs): npm `/root/.npm`, pip `/root/.cache/pip`, Go `/go/pkg/mod` + `/root/.cache/go-build`, NuGet `/root/.nuget/packages`, Bundler `/root/.gem`, Cargo `CARGO_HOME=/var/cache/cargo` + `target/`. pnpm (pnpm docs): `--mount=type=cache,id=pnpm,target=/var/cache/pnpm` with `pnpm install --store-dir /var/cache/pnpm --frozen-lockfile`. apt: `/var/cache/apt` + `/var/lib/apt` with `sharing=locked`, **and** `rm -f /etc/apt/apt.conf.d/docker-clean` (otherwise Debian/Ubuntu images delete the downloads) ([Dockerfile ref](https://docs.docker.com/reference/dockerfile/#example-cache-apt-packages)). For a non-root build user, add `uid=`/`gid=`.

## Version traps
- **Engine 23.0**: BuildKit became the default for Linux images, and the classic builder is deprecated. `DOCKER_BUILDKIT=0` still opts out for now ([deprecated](https://docs.docker.com/engine/deprecated/)). Under the classic builder there is no `RUN --mount`, and all stages up to `--target` get built.
- **Dockerfile frontend minimums**: `RUN --mount` 1.2, `COPY --link` 1.4, secret `env=` 1.10, `COPY --exclude` 1.19, `COPY --parents` 1.20. `# syntax=docker/dockerfile:1` floats to the latest 1.x (1.28.0, 2026-10-07; 1.29.0-rc1 out).
- **GHA cache API v1 shut down on 2025-04-15.** The v2 API needs Buildx ≥0.21.0, BuildKit ≥0.20.0, Compose ≥2.33.1, and Engine ≥28.0.0 (docker driver + containerd store). The error text is `This legacy service is shutting down, effective April 15, 2025`.
- **BuildKit 0.21**: the registry cache defaults to `image-manifest=true`. **Buildx 0.35.0**: adds `reset=true` for `type=local`.
- **build-push-action v6** (2024-06): job summary and build-record artifact on by default. **v7.0.0** (2026-03-05): Node 24, so runners need ≥2.327.1. It removed `DOCKER_BUILD_NO_SUMMARY` (use `DOCKER_BUILD_SUMMARY=false`) and `DOCKER_BUILD_EXPORT_RETENTION_DAYS` (use `DOCKER_BUILD_RECORD_RETENTION_DAYS`).
- **setup-buildx-action v4.0.0** (2026-03-05): Node 24. Removed the `config` input (use `buildkitd-config`), `config-inline` (use `buildkitd-config-inline`) and `install` (use the `BUILDX_BUILDER` env var).
- **buildkit-cache-dance**: Docker's docs still pin v2.1.4 with `cache-source`/`cache-target`. Those inputs are deprecated in v3 (latest v3.4.0, node24), so use `cache-map`/`cache-dir`.
- **docker/github-builder `@v1` (= v1.19.0)**: the default runners are `ubuntu-26.04` / `ubuntu-26.04-arm`. The Docker docs pages still show `ubuntu-24.04(-arm)`. The legacy `auto`/`amd64`/`arm64` runner values emit deprecation warnings.
- **Compose 5.0.0** (2025-12-02): the internal builder was removed, and builds go through Bake. 5.7.0 passes `--parallel` to Bake as `--jobs`.
- **Buildx history**: 0.20 added `history`, 0.21 added `trace` and `inspect --format json`, 0.22 added `^N` offsets and `import`, 0.23 added `export`.
